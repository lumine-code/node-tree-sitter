# Benchmark methodology

The [final standalone quality review](final-quality-review.md) records the field cursor leak fix, memory measurements, API boundary corrections and final performance controls against the previous package revision.

The [pre-integration review](pre-integration-review.md) records a separate baseline/candidate comparison of parser construction, edit preparation, range validation and capture materialization, including remaining integration risks.

The [predicate and node identity review](predicate-performance-review.md) compares ordered edit batches, quantified predicates and ordinary query/cursor controls. It records both the targeted improvements and the remaining cursor traversal regression, with no changes to the vendored Tree-sitter runtime.

Run `node benchmark/wasm.js` on an otherwise idle machine. Each backend runs in a fresh process with the same committed JavaScript Wasm fixture and generated source. The default is 10,000 lines, two warmups and ten measured samples. Results include raw samples, medians, p95, runtime versions and structural checksums. Compare multiple complete runs with reversed or randomized backend order before making a performance claim; the default runner uses a fixed order and is an exploratory benchmark.

Initial parse duration includes synchronous submission and awaiting completion. Submission time measures how long `parse()` occupies the calling thread before returning a tree or promise. Incremental duration includes copying/editing the previous tree, validating changes in the background API and producing the updated tree. The two synchronous backends mutate their prior tree as required by their API; the background backend preserves its published snapshot. All backends parse the same text and the final tree checksums must agree.

Timer gaps are sampled during initial parsing and a short drain afterwards, outside checksum generation and result inspection. They describe JavaScript event-loop availability, not Electron input-to-paint latency. `loadMs` includes module loading, engine initialization and grammar compilation; `firstParseMs` additionally exposes the first parse, including lazy background-store initialization. Steady-state medians exclude warmups. Memory is sampled after explicit garbage collection in each child process and is not peak memory or a direct measure of live tree storage.

Do not interpret faster submission as faster parsing. Wasmtime initialization and native-to-Wasm lexer calls have their own costs; background parsing may improve responsiveness while taking longer to finish than web-tree-sitter. The web baseline calls the library synchronously and does not reproduce Lumine's existing cooperative parse slicing, so timer differences cannot be presented as measured editor improvements. Large-file input copies remain part of the calling-thread cost until a native text-snapshot interface is implemented. Full editor evaluation must additionally cover queries, injections, grammar reload, cancellation storms, memory under many open files and actual frame presentation.

An exploratory Windows x64 run is saved in [the initial result file](../benchmark/results/2026-10-17-windows-x64.json), including raw samples and its source revision. On that run, initial parse medians were approximately 53.5 ms for web-tree-sitter, 72.5 ms for native synchronous parsing and 70.5 ms for native background parsing; background submission took approximately 0.08 ms. Native parsing did not win on total duration. The machine was not isolated from other workloads, so these are preliminary observations rather than acceptance measurements or a product performance claim.
